# 유관기관 SSO/IM 연동 가이드 (중기원패스 BFF 모델)
_작성일: 2026-04-22_

## 1. 문서 목적
- 본 문서는 유관기관 시스템 연동을 `중기원패스(BFF)` 중심으로 재정의한 구현 가이드다.
- `Q-Sign`은 중기원패스 백엔드를 통해 사용되는 인증 인프라로 본다.
- `Q-IM`은 최소 외부 노출 원칙으로 운영하며, 일반 SSO/IM 모델의 IM 역할(통합 회원/매핑/속성 관리)을 담당한다.

## 2. 아키텍처 정의

### 2.1 역할
1. 유관기관 FE(`smep-ufe`)
- 사용자 UI
- 로그인 시작/콜백 처리 화면
- 백엔드 API 호출

2. 유관기관 BE(`smep-be`, BFF)
- 인증 오케스트레이션 핵심
- Q-Sign 토큰 교환/검증
- Q-IM 조회/매핑
- 유관기관 내부 토큰(또는 세션) 발급

3. Q-Sign
- OIDC/OAuth2 IdP
- 인증/인가 코드 발급
- 토큰 엔드포인트 제공

4. Q-IM
- 통합 회원/기관 매핑 시스템(IM)
- 최소 엔드포인트만 외부 노출
- 실질적으로는 BFF에서만 호출

### 2.2 네트워크 원칙
1. 외부 사용자/브라우저가 직접 접근하는 유일한 업무 진입점은 유관기관 FE
2. 유관기관 BE는 외부 직접 callback 공개를 지양
3. Q-Sign/Q-IM 직접 호출은 BE에서 수행
4. Q-IM 공개 범위는 최소 API로 제한

## 3. 표준 로그인 시퀀스 (BFF)

### 3.1 전체 흐름
1. 유관기관 FE 로그인 버튼 클릭
2. FE → BE `GET /api/v1/auth/login-url`
3. BE가 Q-Sign authorize URL 생성 후 FE에 반환
4. FE가 팝업/새창으로 Q-Sign 인증 페이지 이동
5. 인증 완료 시 Q-Sign이 FE callback(`/oauth/callback`)으로 `code/state` 리다이렉트
6. FE callback 페이지 → BE `POST /api/v1/auth/exchange` (`code/state` 전달)
7. BE가 Q-Sign token endpoint와 서버-서버 통신으로 토큰 교환
8. BE가 Q-IM 최소 API 호출로 통합 회원/기관 매핑 조회
9. BE가 유관기관 업무용 토큰/세션 생성 후 FE callback에 응답
10. FE callback이 부모창으로 `postMessage(LOGIN_SUCCESS|LOGIN_ERROR)` 전달 후 종료
11. FE 부모창이 상태 저장소(`useAuthStore`)에 로그인 반영

### 3.2 핵심 결론
- Q-Sign이 유관기관 BE를 직접 호출하는 모델이 아니다.
- 브라우저 리다이렉트는 FE callback으로 받고, 민감한 교환/매핑은 BE에서 처리한다.

## 4. API 계약 (유관기관 FE ↔ BE)

### 4.1 로그인 시작
`GET /api/v1/auth/login-url`

응답 예시:
```json
{
  "loginUrl": "https://qsign.example/.../authorize?...",
  "state": "opaque-state",
  "nonce": "opaque-nonce"
}
```

### 4.2 코드 교환
`POST /api/v1/auth/exchange`

요청 예시:
```json
{
  "code": "auth-code",
  "state": "opaque-state",
  "redirectUri": "https://{fe-domain}/oauth/callback",
  "codeVerifier": "pkce-verifier-if-used"
}
```

응답 예시:
```json
{
  "accessToken": "agency-jwt",
  "refreshToken": "agency-refresh-token",
  "profile": {
    "id": "user-id",
    "name": "홍길동",
    "email": "user@example.com",
    "currentCompany": {
      "companyId": "C001",
      "companyName": "샘플기업",
      "bizNo": "1234567890",
      "role": "ADMIN"
    },
    "linkedCompanies": []
  }
}
```

### 4.3 세션 유지/종료
1. `POST /api/v1/account/refresh`
2. `POST /api/v1/auth/logout` (또는 `/api/logout`)
3. `GET /api/v1/account/me`

## 5. FE callback 및 postMessage 규격

### 5.1 FE callback 라우트
- `/oauth/callback` (유관기관 FE 내부 라우트)
- 책임:
1. URL 파라미터 `code/state/error` 파싱
2. `/api/v1/auth/exchange` 호출
3. 결과를 `window.opener.postMessage`로 부모창 전달
4. 팝업 종료

### 5.2 메시지 스펙
성공:
```json
{ "type": "LOGIN_SUCCESS", "token": "agency-jwt", "data": { "..." : "..." } }
```

실패:
```json
{ "type": "LOGIN_ERROR", "message": "로그인 실패 사유" }
```

보안 규칙:
1. `event.origin` 화이트리스트 검증
2. `targetOrigin` 고정 사용
3. state 미일치/누락 시 즉시 실패 처리

## 6. Q-IM 최소 노출 원칙

### 6.1 Q-IM 역할
1. 통합회원 식별자(global id) 관리
2. 유관기관-기업 매핑 확인
3. 계정 상태(활성/잠금/탈퇴) 판단

### 6.2 노출 전략
1. 공개 API 최소화
- 예: `resolveMember`, `mappingStatus` 수준
2. 외부 직접 호출 주체 제한
- 원칙적으로 유관기관 BE만 호출
3. 네트워크/보안 제어
- IP allowlist, mTLS 또는 API Gateway
- 단기 Access Token 또는 Client Credential 분리

### 6.3 장애 시 정책
1. Q-IM 타임아웃: 인증 성공이어도 업무 진입 제한/지연 정책 명시
2. Q-IM 오류: fallback 금지(임의 계정 생성 금지)
3. 추적성 확보: 요청 ID/회원 ID 마스킹 로그

## 7. smep-ufe 구현 기준 (프로젝트 반영점)

### 7.1 현재 활용 가능한 구성
1. `src/store/useAuthStore.jsx`
- 로그인 상태/토큰/프로필 저장
- 탭 간 로그아웃 동기화
2. `src/lib/apiClient.js`
- Authorization Bearer 자동 주입
3. `src/components/ui/Header.jsx`
- 팝업 로그인 및 `postMessage` 수신 기반 코드 존재

### 7.2 수정/정리 우선순위
1. SSO 로그인 진입점 단일화
- 사용자 로그인 버튼은 SSO 경로 하나만 사용
2. callback 페이지 명시적 분리
- `/oauth/callback` 전용 컴포넌트 추가
3. 인증 방식 혼재 제거
- 시나리오용 로그인/SSO 테스트 라우트는 운영 노출 제외
4. 오류 UX 통일
- `LOGIN_ERROR` 메시지 표준 처리

## 8. 테스트 체크리스트

### 8.1 기능
1. 로그인 클릭 → Q-Sign 화면 진입 성공
2. callback에서 exchange 호출 성공
3. `LOGIN_SUCCESS` 수신 후 `useAuthStore.login` 반영
4. 새로고침 후 인증 상태 유지
5. 로그아웃 시 전 탭 동기화

### 8.2 보안
1. origin 불일치 메시지 무시
2. state 불일치 시 로그인 실패 처리
3. 만료 토큰 refresh 실패 시 안전한 재로그인 유도

### 8.3 연동
1. BE의 Q-Sign 토큰교환 성공률
2. BE의 Q-IM 조회 결과와 FE 프로필 매핑 정합성
3. 장애 시 에러코드/메시지 표준화

## 9. 운영 전 점검 항목
1. Q-Sign redirect URI에 FE callback URL 등록 완료
2. BE ↔ Q-Sign 통신 경로 및 인증서 점검
3. BE ↔ Q-IM 최소 노출 API allowlist 점검
4. 감사로그(로그인 시작/교환/매핑/실패) 적재 확인
5. 개인정보/식별자 로그 마스킹 확인
