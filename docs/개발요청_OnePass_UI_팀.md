## OnePass UI의 역할 정확히 이해하기

SSO 시스템을 구성하는 세 계층을 명확히 구분하는 것이 중요합니다.

```
┌─────────────────────────────────────────────────────────────┐
│  계층 1: 사용자 인증 화면 (UI)                               │
│                                                             │
│  onepass.smes.go.kr                                         │
│  ├─ 사용자가 ID/PW를 입력하는 로그인 화면 제공              │
│  ├─ 회원가입, 비밀번호 찾기 화면 제공                       │
│  └─ ※ 인증 결과(토큰/쿠키) 자체는 발행하지 않음            │
└─────────────────────────────────────────────────────────────┘
                         │ UI 입력값 전달
                         ▼
┌─────────────────────────────────────────────────────────────┐
│  계층 2: 인증 서버 (IdP)                                     │
│                                                             │
│  isso.smes.go.kr (QSign / Keycloak)                        │
│  ├─ 실제 자격증명(ID/PW) 검증                               │
│  ├─ KEYCLOAK_SESSION 쿠키 발행 ← SSO의 핵심               │
│  ├─ authorization_code 발급                                 │
│  └─ access_token / refresh_token / id_token 발급           │
└─────────────────────────────────────────────────────────────┘
                         │ 토큰 발급
                         ▼
┌─────────────────────────────────────────────────────────────┐
│  계층 3: 서비스 제공자 (SP)                                  │
│                                                             │
│  각 유관기관 시스템 (기관포털A, 기관포털B 등)                │
│  ├─ code → 자체 JWT 발급                                    │
│  ├─ 사용자 정보 조회 및 매핑                                 │
│  └─ 서비스 제공                                             │
└─────────────────────────────────────────────────────────────┘
```

**한 줄 요약**: OnePass UI는 **"얼굴"**, QSign은 **"두뇌"** 입니다.  
사용자는 OnePass 화면에서 로그인하지만,  
실제 인증과 SSO 쿠키 발행은 QSign이 담당합니다.

## 전체 로그인 흐름 (OnePass 관점)

```
사용자가 기관포털A에서 "로그인" 클릭
        │
        ▼
기관포털A FE → QSign Auth URL로 redirect
  GET https://isso.smes.go.kr/qsign/realms/ucube-qsign/
      protocol/openid-connect/auth
      ?client_id=기관A-client-id
      &redirect_uri=https://www.portal-a.go.kr/sso/callback
      &response_type=code
      &scope=openid
      &state=무작위값
        │
        ▼ QSign 처리:
        ├─ KEYCLOAK_SESSION 쿠키 있음 → 이미 SSO 세션 존재
        │         → OnePass 화면 없이 즉시 code 발급 (SSO)
        │
        └─ KEYCLOAK_SESSION 쿠키 없음 → 최초 로그인 필요
                  → OnePass UI로 로그인 화면 위임  ← 여기서 OnePass 등장
                          │
                          ▼
              onepass.smes.go.kr 로그인 화면 표시
                  ┌─────────────────────────┐
                  │  중기 통합회원 로그인    │
                  │  아이디: [________]      │
                  │  비밀번호: [________]    │
                  │  [로그인]  [회원가입]    │
                  └─────────────────────────┘
                          │ 사용자 ID/PW 입력
                          ▼
              QSign: 자격증명 검증
                  → 성공: KEYCLOAK_SESSION 쿠키 발행
                          + code 발급
                          + 기관포털A redirect_uri로 이동
                  → 실패: 오류 메시지 표시 (OnePass 화면 유지)
```

## 1. state 파라미터 보존 확인 (CSRF 방어 핵심)

### 왜 중요한가?

`state`는 CSRF(Cross-Site Request Forgery) 공격을 방어하는 OIDC 표준 보안 파라미터입니다.  
각 유관기관 FE는 로그인을 시작할 때 `state` 값을 생성하여  
Auth URL에 포함시키고, QSign 콜백으로 **동일한 state** 값이 반환되는지 검증합니다.

```
[state 검증 정상 동작]

기관포털A FE:
  1. 무작위 state 생성: "x7k2p9m1"
  2. sessionStorage에 저장: { keycloak_state: "x7k2p9m1" }
  3. Auth URL 생성:
     GET .../auth?...&state=x7k2p9m1

QSign:
  4. 사용자 인증 처리
  5. 콜백 발행:
     GET https://portal-a.go.kr/sso/callback?code=XXX&state=x7k2p9m1
                                                          ↑ 동일값 반환

기관포털A FE:
  6. sessionStorage["keycloak_state"] == "x7k2p9m1" 비교
  7. 일치 → 정상 처리 ✅
  8. 불일치 또는 없음 → CSRF 공격 의심 → 로그인 거부 🚫
```

```
[state 값이 변형되거나 누락될 경우]

만약 QSign과 OnePass 사이의 인증 위임 과정에서
state 값이 변형되거나 누락된다면:

→ 모든 유관기관 FE의 state 검증이 실패
→ 모든 로그인 시도가 CSRF 공격으로 판단되어 거부됨
→ state 검증을 비활성화할 수밖에 없음 → 보안 취약점 발생
```

### 현재 상황

일부 유관기관에서 로그인 후 QSign 콜백에 `state`가 포함되지 않거나  
값이 변경된다는 보고가 있어, 현재 state 검증을 **임시 비활성화**한 상태입니다.  
이는 보안상 허용되지 않는 임시 조치이므로 **반드시 해소**되어야 합니다.

### 요청 사항

1. **state 파라미터 보존 테스트 수행 및 결과 공유**

   아래 테스트를 직접 수행하거나, 수행할 수 있도록 테스트 환경을 제공해 주세요.

   ```
   테스트 방법:
   
   Step 1. 아래 URL을 브라우저에서 직접 열기 (테스트 client_id 사용)
     https://isso.smes.go.kr/qsign/realms/ucube-qsign/
       protocol/openid-connect/auth
       ?client_id=[테스트 client_id]
       &redirect_uri=[등록된 테스트 redirect_uri]
       &response_type=code
       &scope=openid
       &state=TEST-STATE-12345   ← 이 값이 콜백에 그대로 반환되어야 함
   
   Step 2. OnePass 화면에서 로그인 완료
   
   Step 3. redirect_uri로 이동된 후 URL 파라미터 확인
     기대값: ?code=XXX&state=TEST-STATE-12345
     문제 있음: ?code=XXX  (state 누락)
               또는 ?code=XXX&state=다른값 (state 변형)
   ```

2. **OnePass UI 인증 위임 과정에서 state 처리 방식 확인**
   - QSign이 OnePass에 로그인 화면을 위임할 때 state를 어떻게 전달하는지
   - OnePass 인증 완료 후 QSign에 결과를 반환할 때 state가 보존되는지
   - state 변형이 발견된다면 어느 단계에서 발생하는지 원인 파악 및 수정 요청

3. **수정 완료 후 테스트 결과 문서 공유 요청**

## 2. QSign → OnePass UI 위임 파라미터 및 흐름 문서화

### 왜 필요한가?

유관기관 시스템이 OnePass와의 연동에서 문제가 발생했을 때,  
각 기관 개발팀이 어디서 문제가 생겼는지 디버깅하려면  
QSign과 OnePass 사이의 내부 흐름을 이해해야 합니다.

또한 OnePass 로그인 화면에서 어떤 오류가 발생할 수 있는지,  
그 오류가 최종적으로 유관기관 콜백에 어떻게 전달되는지 알아야  
각 기관이 적절한 오류 처리 UI를 구현할 수 있습니다.

### 요청 사항

아래 내용을 문서화하여 공유해 주세요.

1. **QSign → OnePass 위임 흐름**
   ```
   QSign이 OnePass에 로그인 화면을 위임할 때:
   - 어떤 URL로 이동하는가?
   - 어떤 파라미터가 전달되는가? (예: client_id, redirect_uri, scope 등)
   - OnePass가 받는 파라미터 목록과 각 파라미터의 의미
   ```

2. **OnePass → QSign 인증 결과 전달 흐름**
   ```
   사용자가 OnePass에서 로그인 성공/실패 시:
   - 어떤 방식으로 QSign에 결과가 전달되는가?
   - POST redirect? 쿠키? 직접 API 호출?
   - 이 과정에서 state 파라미터는 어디에 보관되고 어떻게 복원되는가?
   ```

3. **OnePass 화면에서 클라이언트 정보 표시 여부**
   ```
   사용자가 어느 기관에서 로그인을 시도하는지 OnePass 화면에 표시되는가?
   예: "기관포털A 서비스 이용을 위해 로그인하세요"
   → 표시된다면: client_id 기반으로 자동으로 표시되는가? 별도 설정이 필요한가?
   → 표시되지 않는다면: 설정으로 활성화할 수 있는가?
   ```

## 3. 로그인 후 사용자 정보(Claims) 제공 범위 확인

### 왜 필요한가?

각 유관기관은 로그인한 사용자가 **자기 시스템에서 유효한 회원인지**,  
**필요한 정보를 모두 등록한 상태인지**를 확인해야 서비스 제공이 가능합니다.

이 정보는 QSign의 `id_token` 또는 `userinfo` 엔드포인트를 통해 제공받을 수 있으며,  
OnePass가 관리하는 회원 속성이 Claims에 포함되어야 각 기관이 별도 API 없이  
이 정보를 활용할 수 있습니다.

```
[Claims 정보가 없을 때의 문제]

기관포털A:
  로그인 완료 → access_token 발급
  → 사용자 정보 조회 API 별도 호출 필요
  → 응답에 "추가정보 미등록" 여부 없음
  → 별도 API를 만들어야 함 (개발 비용 증가)
  → 유관기관마다 동일한 로직 중복 구현

[Claims에 포함될 경우]

기관포털A:
  로그인 완료 → id_token 파싱
  → sub: "사용자UUID"
  → profile_complete: false  ← 추가정보 미등록
  → 바로 추가정보 등록 페이지로 안내 (별도 API 불필요)
```

### 요청 사항

아래 정보들이 `id_token` 또는 `userinfo` 엔드포인트에서 제공되는지 확인 후 회신 요청드립니다.

**`id_token` / `userinfo` 표준 Claims 제공 여부 확인**:

| Claim | 설명 | 표준 여부 | 제공 여부 | 제공 방법 |
|-------|------|-----------|-----------|-----------|
| `sub` | 사용자 고유 식별자 (변경 불가 UUID) | OIDC 표준 | ? | |
| `name` | 성명 | OIDC 표준 | ? | |
| `email` | 이메일 주소 | OIDC 표준 | ? | |
| `email_verified` | 이메일 인증 완료 여부 | OIDC 표준 | ? | |
| `phone_number` | 휴대폰 번호 | OIDC 표준 | ? | |
| `birthdate` | 생년월일 | OIDC 표준 | ? | |

**OnePass 전용 커스텀 Claims 제공 여부 확인**:

| Claim | 설명 | 제공 여부 | 없다면 대안 |
|-------|------|-----------|-------------|
| 최초 로그인 여부 | 신규 가입 직후 첫 로그인인지 여부 | ? | |
| 회원 상태 | 활성/잠금/탈퇴/휴면 등 | ? | |
| 추가정보 등록 여부 | 서비스 이용을 위한 추가 정보 등록 완료 여부 | ? | |
| 기관 소속 여부 | 기업 또는 기관에 소속된 사용자인지 여부 | ? | |
| 본인인증 여부 | 실명 본인인증 완료 여부 | ? | |

> 📌 커스텀 Claims는 Keycloak의 **Protocol Mapper**를 통해 추가할 수 있습니다.  
> QSign 관리자 설정 → Clients → [Client ID] → Mappers 탭에서 추가 가능합니다.  
> OnePass에서 관리하는 사용자 속성을 Claims에 매핑하는 설정이 필요하다면  
> QSign 팀과 협의가 필요합니다.

**Claims 확인 방법 (테스트 요청)**:

```bash
# 1. access_token 획득 후 userinfo 엔드포인트 호출
curl -H "Authorization: Bearer {access_token}" \
  https://isso.smes.go.kr/qsign/realms/ucube-qsign/protocol/openid-connect/userinfo

# 2. id_token을 Base64 디코딩하여 Claims 확인
# id_token은 JWT 형식: header.payload.signature
# payload 부분을 Base64 디코딩하면 Claims 확인 가능
echo "{id_token_payload}" | base64 -d | jq .
```

## 4. 신규 회원가입 후 연동 기관으로 복귀 처리

### 왜 필요한가?

기관포털A에 처음 접속하는 신규 사용자는 OnePass 계정이 없어  
로그인 화면에서 "회원가입"을 클릭하게 됩니다.  
회원가입 완료 후 사용자가 자동으로 기관포털A에 로그인되어  
서비스를 이용할 수 있어야 UX가 완성됩니다.

```
[복귀 처리가 없을 경우 — 나쁜 UX]

기관포털A 접속 → 로그인 클릭 → OnePass 로그인 화면
→ "회원가입" 클릭 → 회원가입 완료
→ ??? 어디로 가야 하는가?

→ 기관포털A 홈페이지로 이동? → 로그인이 안 된 상태
→ OnePass 메인으로 이동? → 사용자가 다시 기관포털A를 찾아야 함
→ 혼란스러운 경험 ❌

[복귀 처리가 있을 경우 — 올바른 UX]

기관포털A 접속 → 로그인 클릭 → OnePass 로그인 화면
→ "회원가입" 클릭 → 회원가입 완료
→ QSign이 자동으로 기관포털A redirect_uri로 code 발급
→ 기관포털A: code로 JWT 발급 → 로그인 완료 → 서비스 이용 시작 ✅
```

### 요청 사항

1. **회원가입 완료 후 QSign 콜백 전달 동작 확인**
   ```
   테스트 시나리오:
   1. 기관포털A에서 로그인 시작 (신규 사용자 기준)
   2. OnePass 로그인 화면에서 "회원가입" 클릭
   3. 회원가입 완료
   
   기대 동작:
   → QSign이 기관포털A의 redirect_uri로 code 발급
   → https://www.portal-a.go.kr/sso/callback?code=XXX&state=무작위값
   
   실제 동작 확인 후 결과 공유 요청
   ```

2. **회원가입 중 원래 기관으로 돌아가기 처리**
   ```
   사용자가 회원가입 도중 "취소" 또는 브라우저 뒤로가기 클릭 시:
   → 기관포털A 로그인 페이지로 복귀되는가?
   → 아니면 OnePass 또는 QSign 오류 페이지로 이동하는가?
   
   이상적인 동작:
   → 기관포털A callback에 error=access_denied 전달
   → 기관포털A가 로그인 페이지를 표시
   ```

3. **이메일 인증 필요 회원의 처리**
   ```
   회원가입 후 이메일 인증이 필요한 경우:
   → 이메일 인증 완료 전에는 code 발급이 안 되는가?
   → 이메일 인증 전 상태에서 기관포털A로 어떻게 응답하는가?
   
   각 기관이 이 케이스에서 어떻게 처리해야 하는지 가이드 요청
   ```

## 5. 로그아웃 연동 시 OnePass 처리 확인

### 왜 필요한가?

유관기관 시스템에서 로그아웃 시 QSign에 `id_token_hint`를 포함하여  
로그아웃 요청을 보내면, QSign이 `KEYCLOAK_SESSION` 쿠키를 삭제합니다.

이 과정에서 OnePass가 별도로 관리하는 세션이 있다면,  
OnePass 세션도 함께 정리되어야 완전한 로그아웃이 이루어집니다.

```
[로그아웃 미완전 케이스 예시]

사용자: 기관포털A에서 로그아웃
→ QSign: KEYCLOAK_SESSION 쿠키 삭제

동일 브라우저에서 기관포털B 접속
→ QSign으로 이동 → KEYCLOAK_SESSION 없음 → 로그인 필요
→ OnePass 로그인 화면으로 이동
→ OnePass가 별도 세션을 유지하고 있다면?
   → OnePass가 자동으로 로그인 처리 → 사용자는 로그아웃한 줄 알았는데
     다시 OnePass 세션으로 자동 로그인 ❌

→ 완전한 로그아웃을 위해서는 OnePass 세션도 함께 정리되어야 함
```

### 요청 사항

1. **OnePass 독립 세션 존재 여부 확인**
   - OnePass가 별도의 사용자 세션을 유지하는가?
   - 유지한다면: 쿠키 이름, 도메인, 유효시간은?
   - QSign 세션 만료 시 OnePass 세션도 자동으로 만료되는가?

2. **소셜 로그인(간편 로그인) 연동 사용자의 로그아웃 처리**
   ```
   시나리오:
   사용자가 카카오/네이버/구글 등 소셜 계정으로 OnePass에 가입한 경우
   
   → 기관포털A에서 로그아웃 시 소셜 서비스 세션도 만료되어야 하는가?
   → OnePass에서 소셜 로그아웃을 별도로 처리하는가?
   → 처리한다면 어떤 방식으로 동작하는가?
   ```

3. **QSign Back-Channel Logout 이벤트 수신 시 OnePass 처리**
   ```
   시나리오:
   유관기관 BE가 QSign에 back-channel logout을 요청
   → QSign이 OnePass에도 back-channel logout 이벤트를 전달하는가?
   → OnePass가 이 이벤트를 받아 자체 세션을 정리하는가?
   
   현재 동작 확인 후 가이드 공유 요청
   ```

4. **이상적인 완전 로그아웃 흐름 정의 및 공유**
   ```
   QSign, OnePass, 각 유관기관이 각각 어떤 순서로 세션을 정리해야
   모든 시스템에서 완전히 로그아웃이 되는지 흐름 문서 공유 요청
   ```

## 6. 오류 처리 및 오류 코드 명세 공유

### 왜 필요한가?

유관기관 FE는 QSign 콜백에서 `error` 파라미터를 수신하여  
적절한 오류 메시지를 사용자에게 표시해야 합니다.  
어떤 오류가 어떤 상황에서 발생하는지 알아야  
각 기관이 올바른 오류 UX를 구현할 수 있습니다.

```
[오류 처리 필요 케이스]

케이스 1: 잠긴 계정
  콜백: ?error=access_denied&error_description=Account+is+locked
  기관포털 대응: "계정이 잠겨 있습니다. OnePass 고객센터에 문의하세요."

케이스 2: 탈퇴한 계정
  콜백: ?error=access_denied&error_description=Account+is+disabled
  기관포털 대응: "탈퇴한 계정입니다."

케이스 3: 이메일 미인증
  콜백: ?error=access_denied&error_description=Email+not+verified
  기관포털 대응: "이메일 인증 후 로그인해 주세요."

케이스 4: 사용자 로그인 거부 (동의 화면에서 취소)
  콜백: ?error=access_denied
  기관포털 대응: "로그인이 취소되었습니다."

케이스 5: SSO 세션 없음 (prompt=none 사용 시)
  콜백: ?error=login_required
  기관포털 대응: 로그인 페이지로 이동 (정상 케이스)
```

### 요청 사항

1. **OnePass 및 QSign에서 발생 가능한 오류 코드 전체 목록 제공**

   | error 값 | error_description 예시 | 발생 상황 | 기관 대응 방법 권장 |
   |----------|------------------------|-----------|---------------------|
   | `access_denied` | Account is locked | 계정 잠금 | ? |
   | `access_denied` | Account is disabled | 계정 비활성화 | ? |
   | `login_required` | | SSO 세션 없음 (prompt=none) | ? |
   | `interaction_required` | | 추가 사용자 동의 필요 | ? |
   | *(추가 오류)* | | | |

2. **오류 발생 시 리다이렉션 흐름 확인**
   - 오류 시 QSign이 `redirect_uri?error=XXX` 로 이동하는지
   - 아니면 QSign/OnePass 자체 오류 페이지를 표시하는지
   - 유관기관이 처리할 수 없는 오류(예: QSign 서버 오류)의 경우 어떻게 전달되는지

## 7. 기관별 로그인 화면 커스터마이징 지원 여부

### 왜 필요한가?

사용자가 로그인 화면을 보았을 때 "어느 서비스에 로그인하는 것인지"를 인지할 수 있어야  
피싱 공격을 구별할 수 있고, UX도 향상됩니다.

```
[커스터마이징 미적용 — 현재]

기관포털A에서 로그인 → OnePass 화면 진입
  ┌─────────────────────────┐
  │       OnePass 로그인    │
  │  아이디: [________]    │
  │  비밀번호: [________]  │
  └─────────────────────────┘
  → 사용자: "내가 기관포털A에 로그인하려 했는데 
             왜 OnePass 화면이 나오지?" 혼란

[커스터마이징 적용 — 이상적]

기관포털A에서 로그인 → OnePass 화면 진입
  ┌─────────────────────────────────────────┐
  │  [기관포털A 로고]                        │
  │  기관포털A 이용을 위해 로그인해 주세요  │
  │  중기 통합회원 아이디: [________]       │
  │  비밀번호: [________]                   │
  └─────────────────────────────────────────┘
  → 사용자: "기관포털A에 로그인하는 것을 OnePass가 처리하는구나" 명확
```

### 요청 사항

1. **Client별 화면 테마/내용 설정 지원 여부 확인**
   - client_id별로 로그인 화면 상단에 서비스명/로고를 표시할 수 있는가?
   - 지원한다면: 어떤 설정으로 활성화하는가? (Keycloak Admin 설정 or OnePass 별도 설정)
   - 지원하지 않는다면: 향후 지원 계획 및 대안

2. **표시 가능한 커스터마이징 항목 목록 제공**
   - 서비스명 표시
   - 서비스 로고 이미지
   - 로그인 화면 하단 링크 (예: "기관포털A로 돌아가기")
   - 배경색/테마 색상

3. **설정 방법 가이드 제공**
   - 커스터마이징 가능한 경우: 설정 절차 가이드 문서 공유 요청

## 문의 및 협의

요청 사항 중 OnePass 측에서 처리 불가하거나  
QSign 팀과 협의가 필요한 사항은 사전에 알려주시기 바랍니다.

**최우선 처리 요청 항목**:  
**항목 1 (state 파라미터 보존)**은 현재 보안 취약점과 직결되어 있으므로  
테스트 수행 후 결과를 가장 먼저 회신해 주시면 감사하겠습니다.
